Robot Platform 整合架構

一台邊緣電腦執行平台：Gateway、AI Brain 與模型服務。Zenbo（可多台）與 Pepper 透過 Wi-Fi 主動連到平台，各自有獨立的對話，但共用大腦與模型。每個場域的邊緣電腦都裝同一份程式，用場域設定決定開哪些功能，並有自己的知識庫與 Web 管理台。本頁包含架構圖、場域設定、知識庫、管理台、共用技能庫，以及兩個既有專案（zenbo、peper）各要修改的地方。

三種連線

連線方向與協定內容斷線時
Client ↔ GatewayClient 連 Gateway：REST 命令、WS /eventsRBP Command / Response / Event（文件 Phase 3 格式不變）移動中超過 3 秒沒有 heartbeat，Gateway 送 motion.stop
Gateway ↔ Robot Agent機器人主動連：WS /robot（新增的 Robot Link）robot.hello 註冊、heartbeat、命令往下、事件往上機器人：本機 watchdog 停車，自動重連（1→2→4…最長 30 秒）
Gateway：判定離線，取消該台的命令
Brain ↔ 模型 / 雲端邊緣電腦本機 HTTP；雲端 HTTPS / SSE錄音檔 → STT、文字 → LLM、文字 → TTS 音檔LLM 逾時：機器人說固定的「我想一下，請再說一次」，不做任何動作

Robot Link 訊息（新增，放在 protocol/rbp-v1/link）

// 機器人 → Gateway：上線
{"type":"robot.hello",
 "robot_id":"zenbo-02","robot_type":"zenbo",
 "token":"…","agent_version":"11.30",
 "capabilities":["motion.move","head.move",…],
 "limits":{"motion.move":{"distance":{"min":-1,"max":1}}}}

// 每 1 秒
{"type":"robot.heartbeat","robot_id":"zenbo-02",
 "battery":82,"state":"idle","charging":false}
// Gateway → 機器人：同意上線，下發設定
{"type":"robot.welcome","policy":{…},"config":{…}}

// Gateway → 機器人：命令（就是 RBP Command 本身）
{"type":"command","command":{"protocol":"RBP",…}}

// 機器人 → Gateway：事件（就是 RBP Event 本身）
{"type":"event","event":{"type":"motion.completed",…}}

3-4　LLM 的 tool call 怎麼變成機器人動作

Robot SDK 不是協定，也不是直接交給 LLM 呼叫的工具。從 LLM 到機器人之間有三層，各自的使用者不同。

層是什麼例子誰使用
1. 工具清單（Tools）交給 LLM 看的工具說明。由 LLM 代理依「這台的能力 ∩ 場域開關 ∩ 技能的允許 AI 開關」產生robot_motion_move(distance)小慈的 LLM：決定要不要呼叫、帶什麼參數
2. Robot SDKPython 函式庫，把 HTTP、JSON、WebSocket 包成函式robot.move(1.0)邊緣協調層、測試程式、Demo 程式
3. RBP 協定送到 Gateway 的 JSON 格式與 APIPOST /motion/move、WS /eventsRobot SDK 內部，或任何直接打 API 的程式（例如 Web 管理台）
 
sequenceDiagram
  participant L as 小慈 LLM（雲端）
  participant B as LLM 代理（邊緣協調層）
  participant S as Robot SDK
  participant G as Gateway
  participant Z as Zenbo-01
  B->>L: 問題、KB 資料、這台可用的工具清單
  L-->>B: 回覆文字 + tool_call robot_motion_move（distance 1.0）
  B->>B: 檢查：工具在這台的清單內？場域有開？允許 AI 呼叫？
  B->>S: robot.move(1.0, wait=False)
  S->>G: POST /motion/move（RBP Command）
  G->>G: 能力、Safety、State、控制權
  alt 接受
    G-->>S: accepted
    G->>Z: command
    Z-->>G: motion.completed
    G-->>S: motion.completed（WS /events）
    Note over B,L: 成功不回報給小慈
  else 被拒絕（例如 OUT_OF_RANGE）
    G-->>S: rejected
    S-->>B: RobotCommandRejected
    B->>L: ［系統：前進 1.0 公尺沒有完成，超過安全限制］
  end
  • LLM 連不到 Gateway：小慈在雲端，連不進場域內網，也不該讓它連進來。
  • LLM 只能提出要呼叫哪個工具：真正執行前，LLM 代理和 Gateway 各檢查一次。這就是 Robot_Platform.docx Phase 7 說的「AI Brain 不可繞過 Gateway」。
  • 工具清單依機器人而不同：Pepper 會拿到「感恩合十」，Zenbo 不會；場域關掉底盤移動，就沒有 robot_motion_move。
  • 小慈那邊不用改：小慈現在已經送出 robot_ 開頭的 tool_call（回覆 v3 的 8 個工具），目前由 Zenbo APK 自己解析。平台化之後改由邊緣的 LLM 代理解析，工具名稱和格式不變。

功能類別例子誰可以切換關掉時
一般功能語音對話、KB、台語合成、視覺、保存逐字稿場域管理員，在管理台切換，記錄修改人相關模型不載入、不佔 GPU；相關 action 不列入能力清單，AI 也看不到
受管制功能底盤移動、人臉辨識、外網連線、AI 主動做動作要在設定裡填核可人與日期才能開；管理台顯示核可紀錄Gateway 直接回 UNSUPPORTED_ACTION
某台機器人最後能做什麼 ＝ 這台機器人本身的能力 ∩ 場域開關 ∩ Safety Policy。Gateway 用這個結果回覆 GET /capabilities，管理台的按鈕和交給 AI 的工具清單也都依它產生，三個地方不會不一致。

機器人螢幕顯示（可以開關）

Zenbo 的臉部螢幕和 Pepper 的平板，都可以顯示鏡頭拍到的畫面和字幕。兩邊現有程式都已經有這些功能，只是開關方式不同。平台把它們統一成同一組開關。

功能Zenbo 現有程式Pepper 現有程式建議預設類別
字幕（對話內容）SubtitleOverlay、SubtitleActivity，樣式可調（SubtitleStyle）bridge 把逐字稿送到平板，最多保留 40 行開（長輩聽不清楚時有幫助）一般
鏡頭畫面（拍到的臉）CameraStreamer 平常只把畫面串流給手機和電腦；Zenbo 自己的螢幕只有在註冊人臉（EnrollActivity）時顯示。平常顯示要新增：用小視窗放在角落，不蓋住臉鏡頭串流同時給電腦和平板（2026-10-09 起），設定存在機器人上，預設開依場域決定一般
臉上畫框FaceBoxes，畫在串流畫面上待確認開一般
框上顯示認出的名字待確認待確認關受管制（旁人會知道誰是誰）
隱私模式（一鍵全關）FaceGreeter.privacy：關掉畫框與人臉辨識待補關一般，任何操作人員都能開
  • 三層開關：場域預設（site.yaml 的 display）→ 單台覆寫（管理台，操作角色以上）→ 機器人上的隱私模式（現場一鍵，優先於一切）。
  • 隱私模式開啟時：鏡頭畫面、畫框、名字、人臉辨識全部關閉；字幕不受影響。
  • 設定存在機器人上：重開機後保留（Pepper bridge 已經這樣做），並在 heartbeat 裡回報。管理台顯示的是機器人回報的實際狀態，不是「應該」的狀態。
  • AI 不能開關：這些設定不放進 LLM 的工具清單，只有人能在管理台或機器人上操作。
  • 只顯示、不留存：在機器人螢幕上顯示鏡頭畫面，不等於錄影或上傳。管理台看即時畫面是另一個權限（操作角色以上），同樣受隱私模式管制。

Web 管理台

原則：機器人做不到的動作就不提供，不自動拿別的動作硬湊。要不要做替代版，由人決定後寫進 YAML。

做不到的技能：誠實回應（2026-10-17 決定先採用）

每個技能可以有一句 unsupported_reply。使用者要求某個技能，而這台機器人沒有對應版本時，由 AI Brain 處理，不交給 LLM 自由發揮，避免它答應了卻沒有做。

  • 判斷方式：沿用技能判斷的觸發詞、尊稱規則與語意判斷。判斷出的技能在這台的清單裡沒有，而且有寫 unsupported_reply，就唸這句。
  • 整句只是在要求這個動作：直接唸，不送小慈。
  • 句子還有其他內容：先唸這句，再把整句送小慈，並附註「這個動作已回覆做不到，請不要再答應」。
  • LLM 自己想用：工具清單本來就沒有這個技能，LLM 呼叫不到；萬一送出 tool_call，LLM 代理一律不執行（見 3-4）。
  • 適用所有機器人：不只 Zenbo，例如 Reachy Mini 沒有底盤、Pepper 在底盤未修好前不能移動，都用同一個機制。
現有程式的發現：ZenboControl 已經有自製的 Bow 動作（低頭約 4 秒）和「感恩」表情（Face.THANKS）。人臉辨識認出上人時，會用它們說「上人好，感恩上人。」（FaceGreeter.kt）。所以 Zenbo 其實已經有一個低頭致意的版本，只是不是由語音觸發。之後如果決定做替代版，可以直接沿用，不必重新開發；但是否沿用、名稱怎麼叫，仍需要負責禮儀的人核可。

哪些東西搬到哪裡

  • 執行引擎放在邊緣 Gateway 的 Skill Manager，只有一個。每一步都走 Router、Safety、State 的檢查，所以控制權、急停、限制值一樣有效。取代 Skills.kt 和 Pepper skills.py 的執行部分。
  • 判斷要用哪個技能放在 AI Brain，所有機器人共用：觸發詞（KEYWORDS）、尊稱問好規則（GREET_RES）、語音辨識聽錯的修正（fix_heard 把「何時」改回「合十」）、e5 + bge 語意判斷。
  • Pepper 的安全規則改成平台規則：兩個開關預設關；喚醒、休息、關閉自主模式不准 AI 呼叫；一則回答最多 3 個技能；底盤移動一定要使用者明確要求；「AI 呼叫技能」總開關每次啟動都回到關閉。

8-4　Jetson Orin NX 16GB 評估

優點
  • 約 25～40W，體積小、安靜，好放在場域機櫃。
  • 臺灣品牌，維修和溝通比較方便。
  • Jetson 本來就常用來跑 YOLO 這類視覺模型。
  • 500 GB SSD 足夠放模型權重與資料。
要注意
  • 16 GB 由 CPU 和 GPU 共用，扣掉系統與平台，模型大約只剩 10 GB。
  • 記憶體頻寬約 102 GB/s，約是高階顯示卡的十分之一。台語 TTS 的速度是最可能不過關的項目。
  • 157 TOPS 是 INT8、稀疏運算的數字，不能直接拿來和顯示卡比。
  • ARM 加 JetPack：faster-whisper 沒有現成的 GPU 安裝包，要用 jetson-containers 或自己編譯；PyTorch 要用 NVIDIA 的 Jetson 版本，Pepper 已鎖定的套件版本要全部重新驗證。
  • 現有程式的 Windows 專用部分（.ps1 腳本、Windows 本機語音）要改寫。

向廠商確認：支援的 JetPack 版本（Super 模式要 6.2 以上）與之後的更新由誰提供；長時間全速運作時散熱是否足夠、會不會降頻；有沒有有線網路孔；保固與故障處理方式。

8-5　怎麼決定

  1. 先回答四個問題：每個場域最多幾台機器人同時互動？要不要台語合成？要支援幾種語言？小慈斷線時要不要本機 LLM 備援？
  2. 在候選機器上跑同一支量測工具：現有 Pepper 控制台電腦當比較基準，再加上 Jetson Orin NX 16GB 等候選機器。先借或只買一台，不要直接採購多台。
  3. 依下表判斷是否合格，再對照 8-2 決定各場域的等級。
量測項目合格標準（建議）
本機處理時間（STT + 技能判斷 + TTS，不含小慈）2～3 秒以內

實作順序

每一步都有可以驗收的 Demo。前一步沒過，不進下一步。

  1. 專案與分工。建立共同的 git 專案、保護 main 分支、設定 CODEOWNERS 與共同的 CLAUDE.md（見 11-2、11-3），把兩邊現有程式封存成整合前的基準版本。驗收：兩組都能用 PR 合併，改到別組資料夾時會自動要求該組審核。
  2. 規格與骨架。兩組一起審定 protocol/rbp-v1（含 link），凍結成 v1.0；放入兩個專案的原始碼（不含建置產物）。驗收：Schema 能驗證文件裡所有範例 JSON，兩組都已簽核規格。
  3. 邊緣 Gateway + 模擬機器人。用 Python 寫 Gateway，加上一個假的 Robot Agent。驗收：文件的 Demo 1～8 在模擬器上全部通過，做成 conformance test。
  4. 硬體量測。寫量測工具，在現有 Pepper 控制台電腦與候選機器（例如 Jetson Orin NX 16GB）上各跑一次。驗收：每台候選機器都有一份報表，對照 8-5 的標準決定採購。這一步可以和下一步同時進行。
  5. 整合前確認（和上兩步同時進行）。Pepper 組做 11-1 的 4 項技術確認與現況盤點；Zenbo 組做連線方向改造的確認。驗收：兩組各交一份確認報告，列出可行與要換做法的項目。
  6. 第一台接上平台。Zenbo 或 Pepper，看哪組先有人力：Zenbo 先接，架構最快得到驗證；Pepper 先接，最多功能最快上平台。以 Zenbo 為例：做 RobotLink.kt 和平台模式切換、修正 watchdog。驗收：真機跑 Demo 1～8，另外加上「拔掉邊緣電腦網路線，機器人會停」。
  7. 兩台 Zenbo。Registry、Lease、群組命令、全部急停。驗收：兩台同時被不同 client 控制、互相搶控制權時會被擋、一鍵全停。
  8. Web 管理台與場域設定。把 Pepper 控制台的總覽、設備、異常、手動控制改成多機版，載入 site.yaml。驗收：在管理台關掉 vision 後，YOLO 不再載入，能力清單少了 vision.*。
  9. 第二台接上平台（以 Pepper 為例）。bridge 加 WS link 和對照表，只回報目前已能用的能力（底盤修好前不含 motion.*）。驗收：同一支 Python 程式只改 robot_id，就能讓 Pepper 說話、轉頭；不支援的動作回 UNSUPPORTED_ACTION。
  10. Brain 搬到邊緣電腦。Session、Arbiter、STT 統一、LLM 代理、KB 兩層檢索。驗收：兩台 Zenbo 放在同一間，一句話只有一台回答；偵測到人只打一次招呼；問場域 KB 裡的門診時間，回答附來源。
  11. 共用技能庫。Pepper 的技能轉成 YAML，由 Gateway Skill Manager 執行。驗收：同一個「迎賓」在 Zenbo 和 Pepper 各自用自己的動作完成；「感恩合十」不會出現在 Zenbo 的清單。
  12. 退役舊路徑。平台模式改為預設；移除 APK 裡的金鑰；Pepper 控制台改用 Gateway。
